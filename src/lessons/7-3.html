An API call

Apps talk to models through an API, which is a set of rules that lets one program ask another program for something. Your code sends instructions and messages, and it gets a reply back. A typical request looks like this. The details differ from company to company.

{
  "model": "a-model-name",
  "system": "You are a friendly tutor for beginners. Answer in under 100 words.",
  "messages": [
    { "role": "user", "content": "What is a context window?" }
  ],
  "max_tokens": 300
}

The system prompt sets the model's role, tone and rules for the whole conversation. Two things make results much more reliable. One is putting one or two worked examples in the prompt, which is called few-shot prompting. The other is asking for a fixed format, such as JSON.

Retrieval-augmented generation (RAG)

A model never saw your own documents in training. RAG lets it answer from them anyway. It works in three steps.

  1. Split the documents into short chunks. Turn each chunk into an embedding, which is a list of numbers that captures its meaning.
  2. When a question comes in, turn it into an embedding too. Then find the chunks whose meaning is closest.
  3. Put those chunks into the prompt. Ask the model to answer only from them and to say which chunks it used.

Prompting, RAG or fine-tuning

Start with a good prompt. Add RAG when the answers depend on your own information or on information that changes often. Think about fine-tuning, which means extra training on your own examples, only when you need the same style or format at a large scale and a prompt can't get you there.

Two safety basics

Keep API keys on a server. Never put them in a web page or app that users can look inside. Also, do not trust documents and web pages. Text inside them can try to give the model orders. This is called prompt injection.
